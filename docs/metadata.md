# Metadata storage

See [managed-copy retirement](managed-copy-retirement.md) for public local-only removal, handle invalidation, retry/restart, and the async projected eviction API.

Each file-system root stores metadata in `metadata.redb`, managed by the public `ofdb-kv` facade in its `metadata` table. `FileSystem::open` uses `Database::open_with_table` so existing metadata remains in place.

Filesystem exchange is caller-supplied through `Transport` and `FileSessionService`; this crate has no concrete Iroh adapter or `iroh` feature. Generic messages, versioned metadata codecs, sessions, persistence, reconciliation and memory exchange remain here. See [execution and adapter handoff](execution.md) for the current admission, immutable revision content, cleanup and consumer contracts. Domain resource descriptors, authenticated peer binding, RPC envelopes and network lifecycle belong to the consumer, not persistence.

## Ownership and exchange boundary

`offs` owns filesystem persistence and synchronization/reconciliation semantics: receive, stage, validate, apply, write, and cleanup. `ofdb` supplies the underlying KV persistence and history reconciliation. The caller supplies exchange through the existing `Transport<PeerId>` and `FileSessionService<PeerId>` interfaces; these remain the seam, not a reason to invent another transport trait.

`ofnet/iroh-chain` owns reusable endpoint mesh, generic connections, routing, pairing, and allowlist enforcement. `of` owns domain trust, authenticated identity/resource binding, domain descriptors, protocol-specific exchange integration, and authorization evaluated from the node's local IdP and Management state. It composes adapters over existing `ofnet` facilities rather than duplicating them. `offs` owns generic cancellation and authorization-before-apply execution support, not concrete transport, the policy evaluator or network lifecycle. Local filesystem APIs do not require an online authorization service.

The concrete Iroh adapter is **currently** `crates/file-system/src/iroh_transport.rs`, exposed by the `iroh` feature. Its filesystem exchange integration, domain descriptor, protocol-specific handles/framing/RPC and tests are planned for extraction into `of`, not implemented. Reuse [ofnet/iroh-chain facilities](../../ofnet/crates/iroh-chain/src/server.rs) for generic networking; only actually reusable missing machinery discovered in the usage audit belongs there. Do not blanket move FS protocol codecs or session semantics to `ofnet`, invent new traits, or rewrite networking. Generic filesystem messages/codecs, file sessions, reconciliation, and in-memory test support remain in `offs`. The concrete destination module in `of` will be chosen during coordinated implementation; selecting it is not a planning blocker.

Endpoint allowlist admission is not resource authorization, and pairing is limited bootstrap, not full DB/FS access or domain trust. `of` supplies domain-derived trusted endpoint state and independently evaluates local resource permission; `ofnet` enforces network admission. Locally learned trust removal, revocation, restriction or policy denial must prevent the next affected operation on both peers, including established connections and file sessions. An already-admitted operation may finish; permission is not renewed per chunk.

Mesh message routing does not guarantee transparent multihop DB/FS streams or prove an arbitrary message-origin claim is the authenticated resource actor. Direct connections/streams and routed mesh messages are distinct facilities. Record the actual filesystem exchange path and peer binding during extraction/reconnect validation; do not infer stream forwarding or provider availability through intermediaries.

## Current reconciliation semantics

- `MetadataSync` exchanges complete winning-key `KvSnapshot` sets, including tombstones, on announce and after committed local changes. Lagged messages in the running loop trigger a full exchange. Reconnection requires the caller to start/announce the replacement exchange.
- `Database::import_snapshots` uses a transaction for the supplied snapshot set: a failed import rolls back that set. In the current sibling `ofdb` implementation, older generations are ignored, newer generations replace older ones, and same-generation divergent Automerge histories are merged. This corrects the previous glossary claim that divergence was rejected.
- Paths are metadata keys; content is stored separately under stable file ids. Content revisions are UUIDv7 values separate from KV generations. Revision matching is not a freshness deadline.
- Missing content is fetched from a reachable listed provider through revision-specific file sessions. `store_content` streams to a temporary file, synchronizes it, rechecks the revision, and renames it into place.
- Full/Passthrough and longest-prefix residency remain device-local and process-local per filesystem instance; reopen defaults to Passthrough. Passthrough is read-only and requires an available Full provider for uncached content; becoming Full requires materialization.
- Catalog resource tombstones are distinct from path tombstones. Catalog import retains deletion; projected-copy eviction does not delete the resource for other replicas.

These are specific filesystem semantics over a CRDT-backed KV dependency, not proof of a generic filesystem/content CRDT, byte-wise content merge, or a single atomic content-plus-metadata transaction.

## Target execution contract (not yet implemented)

Every node has local IdP, Management, and Storage capabilities and permits changes locally. Storage CRDT reconciliation has no central authority and no synchronization-freshness expiry. Node composition and local policy evaluation belong to `of`; this migration preserves the filesystem semantics above rather than inventing a new merge model.

Receiving, decoding, staging, or enqueueing remote work does not authorize its later application. Before each new remote apply/write operation, `offs` must use the caller's locally evaluated authorization decision at the actual mutation boundary. Denied or cancelled work must not start a new mutation. An already-authorized operation may finish; a later policy change or cancellation must not interrupt its atomic commit or turn it into a partial write. The next operation needs a new decision. There are no custom quotas, operation timeouts, or deadlines in this contract.

Cancellation stops unstarted work and pending authorization and releases generic staging, file handles, and execution resources. `of` closes protocol streams/tasks/queues using `ofnet` lifecycle facilities where applicable; generic endpoint/connection lifecycle remains in `ofnet`. Invalid, stale, denied, or incomplete content must not replace valid content. Clean up temporary artifacts on success, error, denial, and cancellation; retain earlier committed valid progress. Retaining progress means keeping valid applied metadata and complete content, not promising resumable partial-byte downloads. Existing frame/read/scan shape checks are not authorization quotas or freshness rules.

## Known implementation gaps and verification

`MetadataSync::receive` currently imports snapshots directly; `receive_session` executes filesystem operations without an apply-boundary policy decision. The Iroh adapter checks policy per frame, which is not an apply gate and must not become a mid-operation revocation requirement. `store_content` removes temporary files on selected failures, but stream errors, dropped futures, and other early returns can leave artifacts. Local `write_at`/`append` modify content in place before updating metadata; `write` publishes content before metadata. Their error/crash atomicity is not established by the staging rename used for fetched content.

Generic behavioral and fault-injection tests belong in `offs`; authenticated filesystem Iroh/domain integration tests belong in `of`, and actually reusable networking regressions belong in `ofnet`. Future implementation must demonstrate denial between receive and apply, cancellation before admission and during staging, authorized-operation completion, no partial publication, cleanup, retained valid progress, and offline edits followed by reconnect reconciliation.
