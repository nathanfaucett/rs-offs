# Filesystem operation execution

## Caller interface

`FileSystem::metadata_sync(transport).with_operation_control(control)` installs an `OperationControl<PeerId>`. Construct it with a `Send + Sync` callback `(PeerId, RemoteOperation) -> FileFuture<'static, bool>`. The callback evaluates caller-local policy, not online Management, endpoint allowlisting, or pairing. It is invoked for each imported snapshot set, each destination's outbound metadata request/export (initial announcement, local changes, and snapshot-request replies), and each Open/Read/Write/Scan/Close operation. Every outbound metadata message checks `ExportSnapshots` for its actual destination; no unconditional snapshot broadcast is used. Session decisions include the operation and the peer-scoped handle's resolved path (or `None` for unknown handles). The filesystem/resource binding belongs to the caller configuring this executor; it is not supplied by a remote payload.

The default control permits operations, for caller-controlled local/in-memory exchange. Production callers must install their resource policy. `OperationControl::cancel()` is one-way; clones share cancellation. A replacement executor needs a new control. There are no deadlines, freshness leases, quotas, or chunk renewals.

## Admission and cancellation

Import and session execution acquire the filesystem execution lock **before** consulting policy. Receiving/decoding/enqueueing and opening a handle confer no admission for subsequent operations. Cancellation selects against queued lock acquisition and pending policy. The final cancellation read after policy returns true is the admission linearization point: cancellation visible there wins, otherwise the existing semantic operation is admitted. A policy callback must not call filesystem operations that acquire this execution lock (writes, read/stream, or residency changes); metadata-only `entry`/`revision` inspection does not acquire it.

After mutation admission the executor awaits the mutation to completion without selecting on cancellation. Snapshot import is one supplied-set transaction; a session Write is one offset write and revision update. The baseline embedded redb-backed facade executes its transaction/read/write futures synchronously once polled; there is no detached async storage task or mid-commit cancellation selection. This completion contract uses `cancel()`, not a promise that forcibly aborting a task or killing the process completes it. The content/write failure guarantee below completes this operation boundary.

Outbound metadata transport waits are cancellable through `OperationControl::wait`, including initial requests/deltas, change publication, and snapshot-request replies. Cancellation drops a polled pending send and prevents later sends; it does not retract already delivered messages or undo local commits. A denied destination receives no initial request, snapshot delta, or change publication. Each message rechecks the destination's decision, rather than treating initial admission as permanent permission.

Responses do not authorize operations. A dropped response does not undo a commit. Response backpressure is cancellable **after** operation completion. Cancellation clears executor handles and drains unstarted requests/messages on `pump`; `run` termination drops its executor and receivers. This releases generic resources, not caller-owned transport connections/tasks or ordinary filesystem content. Local Full operations remain available after sync stops.

The execution lock serializes filesystem mutations per `FileSystem` instance (a deliberate throughput ceiling; per-file locking is unnecessary until measured contention warrants it). The owned metadata facade is private to `offs`. No guarantee is asserted for independently opened instances concurrently mutating the same root, cross-store crash atomicity, authenticated domain wiring, or exactly-once RPC.

## Content preparation and publication

Content is now stored as immutable complete files at `.data/<stable-file-id>/<content-revision>`. Metadata selects the visible revision. Overwrite, offset-write and append prepare a new revision separately, synchronize it, publish it, then update metadata. Offset/append copy the previous complete file before modifying the stage; their byte-offset and count semantics are unchanged. Rename prepares content for the destination's new revision before its metadata transaction commits, preserving stable ids and existing metadata-only Passthrough behavior.

A stage guard removes incomplete temporary files and uncommitted published revisions on errors or dropped futures. Old complete revisions remain intact; no rollback has to restore already-overwritten bytes. Reads require the exact selected revision: after newer metadata arrives, old local bytes are not mistaken for that revision. Earlier complete versions are retained until local residency eviction removes the file's content directory. This is retained complete progress, not partial-transfer resumption or a new content-merge model. No legacy flat-content layout adapter/migration is included; existing flat `.data/<file-id>` roots require an explicit separate migration or rematerialization before using this layout.

Fetch uses the existing revision-specific Open/Read-to-EOF exchange. Cancellation selects against provider opening, stream reads, queued publication access and pending policy. On complete transfer it synchronizes staging, acquires execution access, revalidates current file identity/revision, and obtains a fresh `PublishContent` decision from the provider-bound caller control before rename. A denied, cancelled, interrupted or stale transfer removes only its stage. A concurrent completed fetch of the same revision is retained rather than overwritten. EOF closes the generic handle; errors/cancellation/drop release its owned handle. Concrete remote task/stream/session teardown remains the exchange adapter's responsibility.

Proven boundaries are in-process error/cancellation safety and per-instance mutation serialization, including the revision-recheck-to-publication race against imports, writes, rename, deletion and residency changes. The current embedded metadata operation completes synchronously when polled. There is **no** atomic content-plus-database crash transaction, parent-directory durability proof, cryptographic digest verification, or concurrent byte merging. A crash may leave an unreferenced complete version or staging artifact; crash recovery is not asserted by the drop guard. Transfer completion relies on the existing handle's revision-bound Open and EOF contract, not an invented digest/length protocol. Local session reads reject a provider revision change between Read requests instead of mixing versions; an admitted write updates its own handle revision. In-memory exchange requires an explicit `ReadEnd`, so response-channel closure is an interrupted read, not successful EOF.

## Evidence

Transport-neutral integration tests in `tests/admission.rs` cover queued snapshot/tombstone denial and retry, all five established-session operations, pending-policy destruction, deterministic same-poll cancellation/admission, admitted write retention while cancellation releases response backpressure, response loss, and failed snapshot-set rollback preserving earlier imported state. `tests/outbound.rs` covers per-destination initial/change/reply denial and revocation/retry, plus deterministic cancellation and resource release of polled pending sends in announce request/delta, changes, replies and `run` startup. Existing peer-handle, revision, residency, offline and reconciliation regressions remain applicable. `tests/integrity.rs` proves polled multi-chunk cancellation/drop cleanup, stream failure, denial after complete staging, revision change before publication, retry, and exact-revision retrieval retaining earlier bytes. Native tests in `src/file_system_tests.rs` exercise write-after-partial-stage, sync, publication and pre-metadata-completion faults for overwrite/offset/append and fetch, plus cancellation at the native publication checkpoint after session-write admission, cancellation while queued for execution access before policy invocation, provider revision changes between reads, and incomplete read-response closure. Assertions use public fetch/write/read/revision/session behavior; fault checkpoints are test-only. Concrete authenticated transport and local policy integration are consumer responsibilities, not proven by these generic tests.

## Transport-neutral adapter handoff

`file-system` has no Iroh module, re-exports, dependency or feature. The coordinated consumer destination is `of/crates/storage-server/src/filesystem_transport.rs` (of ticket 02); its implementation/build and authenticated reconnect evidence are separate from this owner extraction. No compatibility forwarding module remains. Consumers must remove the `iroh` feature selection and import concrete adapter types and `FILESYSTEM_STREAM_KIND` from their local module, including the marker caller in `data_protocol.rs`.

Implement the existing public `Transport<PeerId>`, `FileSessionService<PeerId>` and `FileHandle<PeerId>` contracts. `FileOperation`, `FileResponse`, `FileHandleId`, `OpenRequest`, `ScanPage`, `SessionRequest` and `SessionResponse` remain public; generic messages retain Serde support. `encode_sync_message`, `decode_sync_message`, `FILESYSTEM_SYNC_PROTOCOL_VERSION` (1) and `MAX_FILESYSTEM_SYNC_FRAME_SIZE` (1 MiB) remain the generic metadata codec contract. The existing `MAX_FILE_READ_LENGTH` (1 MiB) is now public so an adapter can share request-shape validation without duplicating the executor's bound. These are shape limits, not new quotas.

The removed adapter's stream marker (2), version-2 Hello/Metadata/Request/Response envelope, `IrohResourceDescriptor { owner_subject, application_id, filesystem_id }`, pending RPC responses and connection/stream tasks are consumer-owned. Its envelope version is not the generic metadata codec version. Construct a remote handle from the actual `Opened` entry/revision, including when `OpenRequest::revision` is `None`; require `ReadEnd`, not response-channel closure, for successful completion. Keep revision-specific fetch and all apply/staging logic in this crate.

Bind incoming metadata and session requests to the authenticated connection peer, not a claimed payload identity. Install a resource-bound `OperationControl` on the local `MetadataSync`; transport/frame acceptance is not filesystem apply admission. Preserve pending-wait cancellation, completion of admitted mutations and a fresh decision for later queued work. Endpoint allowlisting and pairing admit networking/bootstrap, not resource access. Detailed local execution wiring belongs to of ticket 03; full offline Node acceptance belongs to of ticket 08.

The reuse audit found existing `iroh-chain::Server` endpoint access, router helpers, direct connection/stream APIs, pairing and allowlist hooks. No reusable networking gap was demonstrated and this extraction adds no networking machinery. Consumer composition must use its shared endpoint/router and `Connection::remote_id()`; source inspection is not evidence that composition or authenticated reconnect runs. Direct streams are distinct from routed mesh messages; no multihop stream or arbitrary-origin authentication guarantee is added.
